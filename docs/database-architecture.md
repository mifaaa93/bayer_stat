# Архитектура баз байинга

Срез снят **2 октября 2026** прямым чтением двух MySQL-схем на одном сервере. Учётная запись только на `SELECT`. Локальное хранилище Telegram-бота в этот документ не входит.

Это два слоя:

1. Как базы устроены сейчас и почему сквозная аналитика на них считается неверно, если сложить таблицы как есть.
2. Целевая модель: нейминг, ключи и правила, по которым воронку 1 и воронку 2 можно читать вместе. Набросок Андрея сюда ещё не входил. Когда он появится, сверять с разделом 6, а не переписывать факты раздела 1.

Физические имена схем:

| Воронка в речи | Chatterfy | Схема MySQL | Как бот её называет |
|---|---|---|---|
| Воронка 2, новая | отдельный Chatterfy | `lea_partners_db` | `new` |
| Воронка 1, старая | отдельный Chatterfy | `leadb` | `old` |

Обе схемы — InnoDB, `utf8mb4`. Внешних ключей нет. Почти все идентификаторы, даты и деньги лежат в `varchar` / `text`.

## 1. Что должно происходить в воронке

Так цепочку описал Alex TN 2 октября 2026. Это целевой смысл метрик, а не то, что уже лежит в колонках.

```text
источник (Facebook / Telegram / Google / TikTok)
  → байер получает домен
  → клик
  → лендинг
  → Telegram-инвайтер, кнопка Start          = старт
  → канал, подписка                          = подписчик
  → личные сообщения блогеру                 = чат / лид
  → ссылка на регистрацию                    = регистрация
  → первый депозит трейдера                  = FTD
```

Байер закреплён за доменом. Креатив и кампания именуются байером в кабинете. Расход Facebook байер выгружает из кабинета. Расход Telegram, Google и TikTok пока приносит руками: кабинеты этих источников не парсятся. Chatterfy видит клики, показы, старты, подписчиков, чаты, регистрации и FTD. Расход в Chatterfy не приходит.

Деньги и люди двух воронок считаются отдельно: свои аккаунты, свои домены, свои саппорты, свой Chatterfy. Сверху нужны общие срезы менеджмента: расход, старты, регистрации, FTD, разрез по источнику и байеру, слабый байер, дорогой FTD.

Алерты, которые нужны байеру в его чате:

- плохая конверсия старт → подписчик;
- плохая конверсия чат → регистрация;
- дорогой FTD (расход / число первых депозитов) на дневном срезе;
- тот же дорогой FTD как сигнал, что бюджет уходит не в продукт.

Менеджерский чат спрашивает обе воронки сразу. Чат байера спрашивает только его идентификатор.

## 2. Как это лежит в базах сейчас

Один и тот же набор таблиц загружается в обе схемы. Загрузчик в этом репозитории не лежит, поэтому происхождение колонок восстановлено по составу данных и по тому, как их читает бот.

```text
Chatterfy воронки 2                         Chatterfy воронки 1
        │                                            │
        ▼                                            ▼
 lea_partners_db                                 leadb
   справочники байеров и «блогов»                  те же справочники, другие id
   creos              расход и карточка креатива   creos
   traffers_stat      итог байера за день          этой таблицы нет
   buyer_stats_*      события по имени креатива    buyer_stats_*  (почти те же строки)
   countries*         гео и когорты                countries*
   users_stat         трейдеры этой воронки        users_stat (другие uid)
   common_stats_report итог проекта за день        common_stats_report (другие числа)
                                                   + операторы и KPI, только здесь
```

Бот не копирует рекламу к себе. На каждый вопрос он читает MySQL. Склейка, которой он пользуется: `дата + creo_name` между `creos` и `buyer_stats_today_start_sub`. Источник берётся как `creos.id_blog → bloggers.traf_type`.

### 2.1. Справочники

`traffers` — байер внутри одной схемы. Первичный ключ `id varchar`. Имя в `traffer_name`, статус в `traffer_status`.

Новая схема, 10 человек:

| id | имя | статус |
|---|---|---|
| 0 | NEW_Denys | Работает |
| 1 | NEW_Pavel | Работает |
| 2 | NEW_Chornuy | Работает |
| 3 | NEW_White | Работает |
| 4 | NEW_Svet | Работает |
| 5 | NEW_Anastacia | Работает |
| 6 | NEW_Dima | Пауза |
| 7 | NEW_Nik | Пауза |
| 8 | NEW_Andrey | Работает |
| 9 | NEW_Ilya | Работает |

Старая схема, 23 человека. Рабочие на 2 октября: ТикТок (8), Ilya (10), Denys Polishchuk (12), Svet (17), Farm (18), White (19), VV (20), Corein (21), Nikolai (22). Остальные в «Стоп» или «Пауза». Имена пишутся тремя способами: `NEW_Pavel`, `Denys Polishchuk`, `Спенд Паша`, `Денис ТГ`.

Один и тот же `id` в двух схемах — разные люди. `id=1` в новой схеме — NEW_Pavel, в старой — Спенд Паша. Единственная связь, которая уже зашита в боте: новая учётка `1 / NEW_Pavel` смотрит старый кабинет `18 / Farm`. В имени креатива Farm при этом написано `Pavel`. То есть в старой схеме человек живёт в строке креатива, а `id_traf=18` — это кабинет, не человек.

`bloggers` — не блогер из воронки. Это площадка: бренд плюс источник трафика.

|---|---|---|
| 0 | Леа_фб / фб | Леа_фб / фб |
| 1 | РАМИ_ФБ / фб | Леа_тт / тт |
| 2 | Леа_тг / ТГ | Леа_тг / ТГ |

| 5 | — | РАМИ_ФБ / фб |
| 6 | — | РАМИ_ТГ / ТГ |
| 7 | — | РАМИ_ТТ / тт |
| 8 | — | РАМИ_гугл / Гугл |

`id=1` в новой схеме — РАМИ_ФБ, в старой — Леа_тт. Склеивать схемы по `id_blog` нельзя.

Поля справочника: `blogger` (Леа_фб), `blogger_name` (леа / рами), `traf_type`, `tier`, `kpi`, `rekl_type`, `blogger_status`. `rekl_type` пустой везде. `kpi` везде строка `0.6`. `tier` заполнен только у части строк. `traf_type` не словарь: `фб`, `ТГ`, `тт`, `Гугл`.

### 2.2. Расход и карточка креатива — `creos`

Зерно, которое подразумевается: день + байер + площадка + имя креатива. Фактического уникального ключа нет, и строки повторяются.

| | новая | старая |
|---|---|---|
| строк | 34 188 | 1 021 662 |
| разных ключей день+байер+блог+имя | 31 456 | 1 005 239 |
| дней | 32 (2026-09-01 … 2026-10-02) | 488 (2025-06-01 … 2026-10-03) |
| байеров в факте | 3 | 22 |
| площадок | 2 | 9 |
| разных имён | 983 | 7 589 |
| пустой `budget` | 27 291 | 516 097 |
| числовой `budget` | 6 897 | 505 503 |

Колонки: `date`, `id_traf`, `id_blog`, `id_creo`, `creo_name`, `scenario`, `budget`, `chats`, `subs`, `status`, `month`, `year`.

`date` — текст вида `2026-10-02T00:00:00.000Z`. Это календарный день, не момент UTC. Часовой пояс бота — UTC+2, и день в строке уже бизнес-день.

`budget` — текст. Пустая строка значит «расхода нет в выгрузке». Строка `0` значит ноль и в текущем боте участвует в сумме. На 15 сентября–2 октября в старой схеме ненулевой расход есть только у Farm (`id_traf=18`, РАМИ_ФБ, около $1 159). У Ilya, Denys Polishchuk, White, VV, Corein, Nikolai за те же дни десятки тысяч строк с числовым нулём. Это похоже на заглушку загрузчика, а не на нулевой кабинет.

`id_creo` в новой схеме пустой на всех 34 188 строках. В старой заполнены 324 строки, и там дроби вроде `0.125`, не идентификатор креатива.

`chats` и `subs` на карточке — отдельные числа Chatterfy по этому имени креатива. Их нельзя складывать с `count_sub` из таблицы событий: это другой контур. У новой схемы пустые chats — 18 401 строк, пустые subs — 20 843.

Повторы портят сумму. На 2026-09-01 у креативов вроде `BEFXTRADING` шесть одинаковых строк с одним и тем же `budget`. `SUM(budget)` умножает расход. Перед любой суммой зерно нужно свернуть (одна строка на день + байер + площадка + имя).

Кто реально имеет строки `creos` в новой схеме с 15 сентября: NEW_Anastacia (РАМИ_ТГ, много пустого бюджета, числовой расход около $2 208), NEW_Pavel (РАМИ_ФБ, бюджет заполнен, около $1 416), NEW_Svet (РАМИ_ТГ, бюджет почти пустой). Остальные семь `NEW_*` в `creos` не появляются. Их воронка видна только в `traffers_stat`.

Имена живут в двух языках:

- рекламный кабинет: `USA, Israel, Canada, Bahrain / 26.09 / dking22`, `Bahrain, USA, Canada, Israel / Pavel / 28.09`;
- Telegram-канал или бот: `BEFXTRADING`, `Team_Of_Slash_Forex117`, `Whale200`.

Это не один идентификатор. Совпадение текста — случайность.

### 2.3. События инвайтера — `buyer_stats_today_start_sub`

Колонки: `creo_name`, `count_start`, `count_sub`, `date`, `count_reg`, `count_ftd`. Байера, площадки, источника и страны нет.

| | новая | старая |
|---|---|---|
| строк | 2 950 | 8 029 |
| период | 2026-05-25 … 2026-10-02 | 2026-03-03 … 2026-10-02 |
| разных имён | 803 | 1 403 |

С 1 сентября 2026 это фактически одна лента, записанная в обе схемы:

| с даты | ключей в новой | ключей в старой | общих ключей | из них с теми же четырьмя метриками |
|---|---:|---:|---:|---:|
| 2026-10-01 | 131 | 131 | 131 | 121 |
| 2026-09-22 | 615 | 610 | 609 | 532 |
| 2026-09-01 | 1 180 | 1 172 | 1 164 | 1 038 |

Имена в этой ленте — каналы (`Team_Of_Slash_Forex117`), не кампании Facebook. Сумма двух схем удваивает старты и подписки.

Склейка с `creos` по имени за период с 15 сентября:

- новая схема: 789 из 880 ключей событий нашли креатив, спорных ключей с двумя байерами нет;
- старая схема: 26 из 872, спорных ключей 156.

Поэтому у Facebook-байера Павла таблица событий по объявлениям пустая, и бот берёт итог из `traffers_stat`. У Telegram-байера Анастасии имена каналов совпадают с `creos`, и склейка выглядит рабочей. Это свойство нейминга, не свойство ключа.

### 2.5. Итог проекта за день — `common_stats_report`

Одна строка на календарный день. Первичный ключ `date`.

Колонки: `deps`, `regs`, `ftd`, `withd_count`, `com_count`, `sum_deps`, `sum_ftd`, `sum_withd`, `sum_com`, `chats`. В старой схеме ещё `sum_com_partners`.

Новая: 32 дня, 2026-09-01 … 2026-10-02. Старая: 255 дней, 2026-01-21 … 2026-10-02. Общие 32 дня не совпадают ни по одному дню. Пример 2026-10-01: новая схема 24 регистрации, 3 FTD, 83 чата; старая 13 регистраций, 6 FTD, 16 чатов.

`sum_com_partners` старой схемы на 2026-10-01 равен `916.22` — это `sum_com` новой схемы за тот же день. Похоже на уже сделанную перекидку комиссии между проектами. Пока это не подтверждено загрузчиком, колонку нельзя считать независимым доходом старой воронки.

Этот дневной итог не равен сумме креативов и не равен сумме `traffers_stat`. Для вопроса «сколько вчера было по проекту» берётся эта таблица. Для вопроса «сколько у Павла» она не режется.

### 2.6. Трейдер — `users_stat`

Первичный ключ `uid`. Колонки: `reg_date`, `ftd_date`, `ftd_sum`, `balance`, `tg_id`, `deps`, `deps_count`, `withdrawals`, `withdrawals_count`, `activity_date`, `country`, `report`, `prev_report`.

| | новая | старая |
|---|---|---|
| трейдеров | 52 | 31 730 |
| с датой FTD | 51 | 5 065 |
| с `tg_id` | 52 | 4 462 |
| общих `uid` | 0 | 0 |

Воронки по людям не пересекаются. Байера, креатива, домена и источника у трейдера нет, поэтому когортный FTD «Павел привёл этих людей» из `users_stat` не считается. Даты в новой схеме — `2026-10-01`, в старой встречается `31.12.2025`. Страна то `SA`, то `Saudi Arabia`, то `SY`.

### 2.7. Гео, когорты, выручка

Все суммы здесь снова текст. Страна — полное английское имя, плюс мусорные значения `All` и `1tik` в старой схеме. ISO-коды лежат только в `buyer_stats_today_start_sub_country`.

`countries` — плотная сетка «день × байер × площадка × все страны мира», а не факт расхода. В новой схеме с 1 сентября 45 150 строк, из них ненулевой `spend` у 294, сумма $414.88, и вся она на паре NEW_Pavel + РАМИ_ФБ. Остальные комбинации, включая байеров 0, 2 и 3, забиты нулями. В `creos` у Павла за соседние две недели расход около $1 416. Это разные контуры, меньшая сетка не заменяет кабинет.

`countries_spend` и `countries_spend_month` — неделя или месяц × страна × площадка. `ids_traf` — строка списка, в новой схеме почти везде `0,1,2,3`, в старой `10,12,18,19,21,22,8`. Это состав пула, не доля байера. Порезать такой расход на Павла нельзя.

`countries_revenue`, `countries_revenue_month` — выручка и депозиты по площадке и стране, без байера. `tier` пустой на всех строках. Новая схема: 1 407 недельных и 354 месячных. Старая: 20 061 и 5 282. `id_blog` снова локальный.

Когорты брокера:

| таблица | новая | старая | зерно |
|---|---:|---:|---|
| `countries_cohorts_broker` | 0 | 118 889 | страна, площадка, неделя старта, текущая неделя |
| `countries_cohorts_broker_pivot` | 3 521 | 649 037 | то же + `reg_count` |
| `countries_cohorts_broker_pivot_month` | 357 | 40 030 | месяц |
| `countries_cohorts_broker_uid` | 0 | 5 329 | неделя + страна, без uid в колонках |
| `countries_cohorts_broker_uid_source` | 0 | 1 881 | неделя + `uid` |

Когорта здесь — страна и площадка, не байер и не креатив. Для стоимости FTD конкретного байера она не подходит.

`buyer_stats_today_start_sub_country` — регистрации и FTD по стране и имени креатива. Стартов, подписок и расхода нет. Новая: 155 строк, 2026-09-04 … 2026-10-02, 58 имён, коды стран (`IQ`, `SA`). Старая: 101 строка, 2026-07-01 … 2026-09-28, 15 имён. Байера в таблице нет; бот дописывает его через имя креатива в `creos` и помечает строку спорной, если имя в этот день было у двух байеров или двух площадок.

### 2.8. Таблицы только старой схемы

`buyer_stats_today` — 630 330 строк, 2026-01-20 … 2026-09-28. Только `creo_name`, `count_reg`, `count_ftd`, `date`. 7 171 имя. Без байера. Более ранний контур регистраций, чем лента стартов.

`buyer_stats_country_today` — 134 651 строка, тот же период. Уже есть `id_traf`, `id_blog`, `country`, `count_reg`, `count_ftd`. Это единственная страновая таблица, где байер записан прямо, а не угадывается по имени. В новой схеме её нет.

`buyer_stats_today_start_sub_com` — 7 122 строки, 2026-03-04 … 2026-09-07. Лента стартов плюс `com float`. Обрывается в сентябре.

`buyer_stats_today_start_sub_directbot` — 2 197 строк, 2026-03-16 … 2026-09-24. Имена короткие (`a1`, `a1003`). Отдельный контур прямого бота, в склейку с кабинетом не входит.

`buyers_kpi` — 3 159 строк. Это сетка 39 стран × 9 площадок × 9 байеров, а не факт. Пороги текстом: `cost_ftd`, `cost_reg`, `cost_ls`, `cost_sub`, `cost_start`. Пример: Сирия, площадка 0, байер 8 — FTD $70, регистрация $3.7, старт $0.44. В новой схеме порогов нет. Страны снова в двух написаниях (`SY` и `Yemen`).

`operators`, `operators_ftd`, `operators_smeni` — смены и FTD операторов саппорта. 32 оператора, FTD по 2026-03-17, смены по 2026-04-19. К байеру и креативу не привязаны. В аналитику закупки их не включаем, пока не появится отдельная задача по саппорту.

### 2.9. Служебные и пустые

`spend_fact` — одна сумма на день, без байера и источника. Новая: 29 дней, 1–29 сентября, $8 422. Старая: 133 дня, 1 мая–10 сентября, $112 374.82. С кабинетом `creos` не сходится по определению зерна.

`update_info` — последний удачный прогон загрузчика по `id_traf`: `timestamp_creo`, `timestamp_country`. В новой схеме 6 из 10 байеров. В старой 23, но часть страновых меток застряла в 2025 и весной 2026.

`keitaro_pbs` — пустая в обеих схемах. Колонки `pb`, `status`. Постбеков Keitaro в базе нет.

### 2.10. Чего в базе нет, хотя в речи это есть

- показы и клики Facebook;
- домен и ссылка, выданные байеру;
- отдельное событие лендинга;
- стабильный id креатива и id кампании кабинета;

## 4. Правила, без которых текущие таблицы врут

1. `id` байера и `id` площадки живут внутри схемы. Между `lea_partners_db` и `leadb` они не переносятся.
2. Человек и кабинет — разные сущности. `Farm / 18` — кабинет. Человек в нём пока закодирован словом в `creo_name` (`Pavel`).
3. Ленту `buyer_stats_today_start_sub` не суммируют между схемами: с сентября это один и тот же набор имён.
4. Итог байера (`traffers_stat`), карточка креатива (`creos.chats`, `creos.subs`) и лента каналов — три контура. В ответе называется контур. Контуры не складываются.
5. Пустой `budget` — нет данных. Ноль — записанный ноль. Для старых Facebook-байеров кроме Farm ноль с сентября похож на заглушку; цену FTD по ним не считать, пока загрузчик не разделит «нет выгрузки» и «расход 0».
6. Повтор строки `creos` с тем же бюджетумом умножает `SUM`. Сначала свернуть зерно.
7. Спорное имя (один `creo_name` в один день у двух байеров или двух площадок) не размножают на обоих. В старой схеме таких ключей с 1 сентября — 156.
8. `countries` и `countries_spend` не отвечают на вопрос «сколько потратил байер». Список `ids_traf` — пул.
9. `common_stats_report` — ответ на вопрос про проект. Он не раскладывается на байеров.
10. Когорта байера по `users_stat` невозможна: у трейдера нет байера. Дневной FTD из `traffers_stat` — кассовый (событие в этот день), не когорта привлечения.
11. Страна в одном отчёте пишется одним словарём. Сейчас смешаны `SA`, `Saudi Arabia`, `SY`, `Yemen`.
12. `sum_com_partners` не складывать с `sum_com` новой схемы, пока не разобран загрузчик: на проверенном дне они равны друг другу.

## 5. Что уже умеет бот и где ему тесно

Бот читает новую схему как воронку по умолчанию. Старую открывает только для NEW_Pavel и подменяет байера на Farm `18`. В выборке сейчас два id новой схемы: `1` и `5`. Остальные `NEW_*` в `traffers_stat` уже есть, в список вопросов бота не выведены.

Этого хватает на чат Павла и чат Анастасии с оговорками из раздела 4. Этого не хватает на задачу из голосовых:

- один аналитик на байера с его глобальным id, а не с локальным `id` схемы;
- все источники одним словарём, включая Google и TikTok, а не только те площадки, которые попали в `bloggers`;
- алерты по порогам (порог есть сеткой только в старой схеме и не привязан к боту);
- дневной срез стоимости FTD с явным правилом «нет расхода → нет стоимости»;
- менеджмент: вчера, неделя, источник, худший байер, обе воронки;
- креатив как сущность, а не как подстрока имени.

## 6. Целевая модель

Исходные две схемы не сливаются в одну запись. Их продолжают наполнять два Chatterfy. Поверх них одна аналитическая схема. Бот и алерты читают только её.

Пока нет домена, id кампании и id трейдера с байером, честная склейка «этот показ → этот FTD» не появляется от переименования колонок. Модель ниже фиксирует то, что уже можно посчитать без двойного счёта, и оставляет пустые ключи там, где данных нет.

### 6.1. Имена

| Как говорят сейчас | Имя в аналитике | Комментарий |
|---|---|---|
| воронка 2, новая, `lea_partners_db` | `funnel_2` | отдельный проект и CRM |
| воронка 1, старая, `leadb` | `funnel_1` | отдельный проект и CRM |
| байер, трафер, `traffers` | `buyer` + `buyer_account` | человек и его учётка в воронке |
| блогер, `bloggers`, Леа_фб | `placement` | бренд + источник внутри воронки |
| леа / рами | `brand` | `lea`, `rami` |
| фб, ТГ, тт, Гугл | `traffic_source` | `facebook`, `telegram`, `google`, `tiktok` |
| креатив, `creo_name` | `creative` | сырое имя остаётся атрибутом, не ключом |
| старт | `starts` | нажатие Start в инвайтере |
| подписчик | `subscribers` | подписка на канал |
| чат, лид, ЛС | `chats` | личное сообщение |
| рег | `registrations` | регистрация на платформе |
| FD, FTD | `ftds` | первый депозит |
| бюджет, спенд | `spend_usd` | расход в USD, `NULL` если выгрузки не было |
| карточка chats/subs | `card_chats`, `card_subscribers` | контур креатива, не лента каналов |
| общий отчёт дня | `project_day` | один ряд на воронку и день |

Коды источников и брендов латиницей, в нижнем регистре, без пробелов. Статусы байера: `active`, `paused`, `stopped`. Старые слова «Работает / Пауза / Стоп» остаются в сырой таблице.

### 6.2. Идентичность

`buyer` — человек, один на обе воронки. Его заводят руками. Автосопоставление по похожему имени не делается: в старой схеме рядом живут Denys Polishchuk, Денис ТГ и Спенд Дима.

`buyer_account` — строка `traffers` в конкретной воронке.

Уже известная связь, её и только её можно завести сразу:

| buyer | воронка | локальный id | как называется в схеме | что это на самом деле |
|---|---|---|---|---|
| pavel | funnel_2 | 1 | NEW_Pavel | учётка байера |
| pavel | funnel_1 | 18 | Farm | кабинет; человек дополнительно пишется в имени креатива |

Остальные `NEW_*` заводятся как байеры новой воронки без пары в старой, пока Андрей или Alex не подтвердят пару. Кабинет Farm не становится байером.

`placement` хранит локальный `blogger.id` внутри воронки. Общий ключ площадки — `(funnel, brand, traffic_source)`, а не число `id`.

`creative` получает собственный id. Натуральный ключ внутри воронки: площадка + пространство имени + нормализованное имя.

Пространства имён:

- `ad_campaign` — имя из рекламного кабинета (`… / Pavel / 28.09`);
- `tg_channel` — имя канала или бота (`Whale200`);
- `direct_bot` — короткие коды старой таблицы `directbot`.

Пока нет общего id из Chatterfy, строки разных пространств не соединяются. Когда появится домен, инвайт-ссылка или id кампании Keitaro, они пишутся в `creative_key` и становятся мостом. Таблица `keitaro_pbs` под этот мост пока пустая.

`trader` — `(funnel, uid)`. Общих uid между схемами нет, смешивать их нельзя.

### 6.3. Таблицы аналитики

Сырые схемы остаются источником. Аналитические таблицы либо пересобираются загрузчиком, либо делаются вьюхами. Повторы `creos` снимаются на этом шаге.

**Измерения**

`funnel`
`funnel_id`, `code` (`funnel_1` / `funnel_2`), `crm_name`, `source_schema`

`brand`
`brand_id`, `code` (`lea` / `rami`)

`traffic_source`
`source_id`, `code` (`facebook` / `telegram` / `google` / `tiktok`)

`buyer`
`buyer_id`, `code`, `display_name`, `status`

`buyer_account`
`buyer_account_id`, `buyer_id`, `funnel_id`, `local_traffer_id`, `local_name`, `kind` (`person` / `cabinet`), `status`

`placement`
`placement_id`, `funnel_id`, `local_blog_id`, `brand_id`, `source_id`, `local_name`, `status`

`creative`
`creative_id`, `funnel_id`, `placement_id`, `namespace`, `name`, `name_norm`

`creative_key`
`creative_id`, `key_type` (`domain` / `invite` / `cabinet_campaign` / `keitaro`), `key_value`
Пустая, пока загрузчик не начнёт писать домен. Это и есть будущая сквозная склейка.

`country`
`country_code` ISO 3166-1 alpha-2, `name_en`

`kpi_rule`
`kpi_id`, `buyer_id` NULL, `source_id` NULL, `country_code` NULL, `metric` (`start_to_sub`, `chat_to_reg`, `cpa_ftd`), `operator`, `threshold`, `valid_from`, `valid_to`
Правило действует на самый узкий уровень, который заполнен. Сетка `buyers_kpi` сюда не копируется целиком: из неё переносятся только живые пороги после ревизии. Одинаковые 3 159 комбинаций не считаются настроенным KPI.

**Факты**

`ad_spend_day` — один расход.
Зерно: `stat_date`, `funnel_id`, `buyer_account_id`, `placement_id`, `creative_id`, `country_code` NULL.
Поля: `spend_usd` NULL, `spend_status` (`present` / `missing` / `zero_placeholder`), `load_method` (`cabinet_export` / `manual`), `source_row_hash`.
Страна NULL, пока кабинет не отдал страну отдельной строкой. Нули из сетки `countries` сюда не грузятся.

`funnel_buyer_day` — кассовый итог байера. Источник новой воронки: `traffers_stat`. Для старой воронки строки нет, пока не появится такой же отчёт.
Зерно: `stat_date`, `buyer_account_id`.
Поля: `starts`, `subscribers`, `chats`, `registrations`, `ftds`. Каждое поле NULL, если отчёт за день не приходил. Ноль пишется только если отчёт пришёл и в нём ноль.

`funnel_channel_day` — лента инвайтера. Грузится один раз, не в каждую воронку.
Зерно: `stat_date`, `channel_name`.
Поля: `starts`, `subscribers`, `registrations`, `ftds`, `funnel_id` NULL.
`funnel_id` заполняется только когда у канала есть мост в `creative_key` или однозначная пара с `creative` одного байера. Иначе воронка остаётся пустой, и цифра не приписывается Павелу и Анастасии одновременно.

`creative_card_day` — то, что Chatterfy пишет на карточку рекламного имени.
Зерно: `stat_date`, `creative_id`.
Поля: `card_chats`, `card_subscribers`, `card_status`. Расход здесь не хранится, он лежит в `ad_spend_day`.

`project_day` — бывший `common_stats_report`, строго одна воронка.
Зерно: `stat_date`, `funnel_id`.
Поля: `chats`, `registrations`, `ftds`, `deposits_count`, `deposits_sum`, `ftd_sum`, `withdrawals_count`, `withdrawals_sum`, `commission`, `partner_commission` NULL.
`partner_commission` в воронке 1 не заполняется из `sum_com_partners`, пока не подтверждено, что это не копия комиссии воронки 2.

`trader`
`funnel_id`, `uid`, `tg_id`, `country_code`, `registered_on`, `ftd_on`, `ftd_sum_usd`, `deposits_sum_usd`, `deposits_count`, `buyer_account_id` NULL, `creative_id` NULL.
Последние два поля пустые, пока брокер или Chatterfy не отдадут связь. Без них когортный CPA байера не считается и не подменяется кассовым.

`trader_cohort_week` — текущие когортные витрины брокера, как есть, но с `funnel_id` и ISO-страной. Байера в них нет. Они отвечают на вопрос «как страна окупается у бренда», не «как окупается Павел».

**Алерты**

`alert` пишется расчётом, не руками.
Поля: `stat_date`, `buyer_id`, `funnel_id`, `metric`, `actual`, `threshold`, `severity`, `basis`.
`basis`: `cash` (FTD и расход этого дня или окна) или `cohort` (только когда у `trader` заполнен байер). Пока когорты нет, алерты FTD идут с `basis=cash`, и в тексте так и сказано.

Окно дневного среза для байера: расход из `ad_spend_day` за день, FTD из `funnel_buyer_day` за тот же день. Если `spend_status` не `present`, алерт «нет расхода», а не «бесконечная цена». Если FTD = 0 и расход есть, алерт «расход без FTD», деление не делается.

### 6.4. Какие вопросы чем закрываются

| Вопрос | Откуда | Чего не делать |
|---|---|---|
| Старты Павла за сегодня | `funnel_buyer_day` его учётки | не брать ленту каналов, у Facebook-имён она не его |
| Подписчики и чаты Анастасии | `funnel_buyer_day`; карточка канала отдельно, если нужна | не складывать карточку и отчёт байера |
| Расход Павла за день | `ad_spend_day` со статусом `present` | не добирать нули из `countries` |
| Цена FTD за день | расход `present` / `ftds` того же байера и дня | не делить, если расхода нет; это касса, не когорта |
| Хороший ли креатив | `ad_spend_day` + `creative_card_day` одного `creative_id` | не приклеивать чужие старты по похожему имени |
| Вчера по компании, в разрезе источника | `project_day` по двум воронкам; источник — сумма `ad_spend_day` и `funnel_buyer_day` | проектный день и сумма байеров показываются рядом, если разошлись |
| Слабый байер | сортировка байеров по правилу KPI на одном окне | байер без расхода не становится «лучшим» из-за нулевой цены |
| Google / TikTok | тот же факт, `traffic_source` другой, `load_method=manual` | не заводить третью схему под источник |
| Две воронки в чате менеджера | фильтр `funnel_id` снять | чат байера фильтрует `buyer_id` |
| Когорта «Павел привёл 25 FTD на $1000» | `trader`, когда заполнен `buyer_account_id` | до этого дня в ответе прямо кассовый FTD |

### 6.5. Как жить с двумя базами

Оставляем две сырые схемы. У каждой свой загрузчик и свой Chatterfy.

Аналитическая схема одна. У каждой её строки есть `funnel_id`, кроме `funnel_channel_day`, где воронка может быть неизвестна.

Чат байера привязан к `buyer_id`. Если у человека две учётки, чат видит обе и подписывает воронку. Чат менеджера видит всех байеров и обе воронки.

Сливать `lea_partners_db` и `leadb` в одну физическую базу записи не нужно для аналитики и вредно для загрузчиков: локальные id конфликтуют. Объединение возможно позже как отказ от одной из CRM, это отдельное решение, не миграция отчётов.

### 6.6. Порядок внедрения

1. Завести `buyer`, `buyer_account`, `placement`, словари бренда и источника. Перенести текущие справочники. Связь Pavel ↔ Farm записать как данные и убрать её из кода как единственное место правды.
2. Собрать `ad_spend_day` из `creos` со свёрткой повторов и статусом расхода. Не подмешивать `countries`.
3. Собрать `funnel_buyer_day` из `traffers_stat`. Для старой воронки договориться, откуда возьмётся такой же дневной отчёт. Пока его нет, старая воронка на уровне байера считается только по карточке креатива и расходу кабинета Farm.
4. Загрузить ленту каналов один раз в `funnel_channel_day`. Перестать читать её из обеих схем как две воронки.
5. Собрать `project_day` из двух `common_stats_report`. Разобрать `sum_com_partners` с тем, кто пишет загрузчик.
6. Перевести бота на эти витрины. Чаты байеров, которые уже есть в `traffers_stat`, можно открывать по `buyer_id`, а не по двум зашитым id.
7. Завести `kpi_rule` и дневной расчёт `alert` для трёх метрик из голосовых. Пороги утверждаются отдельно, из старой сетки они сами не становятся нормой.
8. Добавить в загрузчик домен или id кампании и только после этого заполнять `creative_key` и байера у `trader`. Тогда появляется когортный FTD и честный мост «креатив кабинета → канал».

Шаги 1–6 дают корректные ответы на те вопросы, которые данные уже содержат. Шаг 8 — это собственно сквозная аналитика до трейдера. Без него обещать её в чате нельзя.

- Farm — кабинет нескольких людей или уже личный кабинет Павла. От этого зависит, можно ли весь `id_traf=18` отдать одному `buyer_id`.
- Нулевой `budget` у рабочих байеров старой схемы с сентября — это ноль или несгруженный кабинет.
- `buyer_stats_today_start_sub` копируется в обе схемы нарочно или это один канал, который видят оба Chatterfy.
- `sum_com_partners` — доля партнёра или копия комиссии новой воронки.
- Откуда в старой воронке взять дневной итог байера со стартами и чатами, аналог `traffers_stat`.
- Какие пороги алертов боевые, а какие в `buyers_kpi` просто заполненная сетка.
- Список пар «человек в новой схеме → учётка в старой» кроме Павла.
